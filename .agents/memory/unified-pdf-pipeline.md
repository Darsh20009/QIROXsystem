---
name: Unified PDF pipeline
description: Finance documents use one server-side PDF path for downloads and email attachments.
---

All invoice, quotation, and receipt-voucher PDFs should be generated by the shared server PDF service rather than by browser print HTML or a second renderer.

**Why:** The project deploys from a prebuilt server bundle and does not include a reliable Chromium/Puppeteer runtime; one pdf-lib path keeps downloaded files and email attachments consistent.

**How to apply:** Add new finance-document PDF routes and email attachments through the shared service, preserving authenticated access checks and passing current tax, discount, terms, and bank data.

The document TTF used by the server renderer must be copied into the production build output; Vite's client build does not include files that exist only in the repository-level public directory.

**Why:** The development source process could see the repository font while the prebuilt server/frontend runtime could not, causing Arabic or mixed-script measurement to fall back to Helvetica and fail with WinAnsi encoding errors.

**How to apply:** Treat the font as a required build asset, log its resolved path and embedding failure, and fail explicitly rather than measuring Arabic text with a Latin font.

Server PDF modules run under ESM during the development workflow, so path resolution must use `import.meta.url` rather than relying on `__dirname`.

**Why:** The first production-font fix passed a direct CJS-style probe but failed in the actual `tsx server/index.ts` workflow because `__dirname` is undefined there.

**How to apply:** Use `fileURLToPath(import.meta.url)` for module-relative assets and test the renderer through the same workflow mode used by the app.

Arabic PDF text should be reshaped but not manually reversed; reversing the shaped presentation-form string makes otherwise valid Arabic render backwards.

**Why:** The PDF renderer and Amiri presentation forms already produced correct visual RTL order after shaping, while the extra character and word reversal made labels unreadable.

**How to apply:** Keep `arabic-reshaper.convertArabic()` as the single Arabic transformation, use a document font with Arabic, Latin, and symbol coverage, split mixed RTL/LTR runs before drawing, and verify labels, client names, item descriptions, notes, and mixed numeric text visually.

When drawing vector seals with pdf-lib, `drawEllipse` uses `x`/`y` as the center and `xScale`/`yScale` as radii; `width`/`height` are not the ellipse sizing options.

**Why:** Passing `width`/`height` silently produced an oversized seal that collided with the document footer.

**How to apply:** Use center coordinates and `xScale`/`yScale`, then rasterize a generated PDF to verify the seal and signature area stay within the page.

Finance artwork is supplied as independent transparent assets, so render dimensions must follow each embedded image's actual aspect ratio rather than legacy pixel constants.

**Why:** A replacement approval PNG can have a different ratio from the original art, and receipt bank details plus transfer guidance can push the signature into notes or the footer if its space is fixed.

**How to apply:** Derive image sizing from the embedded asset, reserve the footer and approval area after variable receipt content, and visually inspect quotation, invoice, and receipt PDFs after artwork changes.

Shared finance header artwork may include the quotation title as part of the image; invoice and receipt renderers must cover the full embedded title zone before drawing their own dynamic titles.

**Why:** A replacement header can move or widen the baked-in title, leaving quotation text visible beneath a narrower overlay in another document type.

**How to apply:** Check the current header image itself and keep the HTML and PDF title masks aligned with its aspect ratio; leave the embedded title visible for quotations.
