# دليل ربط الأنظمة الخارجية بواتساب QIROX

هذا الدليل يشرح طريقة عمل واتساب في QIROX، وكيف يرسل نظام خارجي رسالة عبر واجهة QIROX الحالية. أُعدّ لمطوّر يتولى تنفيذ الربط من جهة نظامه.

## الخلاصة

- رقم QIROX الداخلي يُربط من صفحة **واتساب CRM** بمسح QR من تطبيق WhatsApp في الهاتف.
- واجهة المشروع الخارجية ترسل من رقم QIROX المتصل، ولا تربط رقم هاتف جديدًا للعميل تلقائيًا.
- لكل مشروع مفتاح API منفصل. يُعرض المفتاح الخام عند الإنشاء أو التدوير مرة واحدة فقط.
- يجب أن يحتفظ النظام الخارجي بالمفتاح في مخزن أسرار الخادم، لا في JavaScript المتصفح أو تطبيق الهاتف.
- لا ترسل إلا إلى مستلمين وافقوا على تلقي الرسائل، ووفّر طريقة لإيقاف الرسائل واحترم طلب الإيقاف.

## 1. طريقة ربط رقم QIROX

1. سجّل الدخول بحساب مدير أو مدير عمليات إلى QIROX.
2. افتح **واتساب CRM** من لوحة الإدارة.
3. اختر **اتصال** ليظهر QR.
4. في الهاتف الذي يملك رقم الإرسال: WhatsApp ← الأجهزة المرتبطة ← ربط جهاز، ثم امسح QR.
5. انتظر حتى تظهر حالة الاتصال ورقم الهاتف في لوحة QIROX.

الـQR يثبت جلسة WhatsApp Web الخاصة برقم QIROX. لا ترسله للمبرمج ولا تحفظ صورة منه في مستودع الكود. حالة الجلسة تُحفظ في قاعدة البيانات بصورة مشفّرة حتى تستمر بعد إعادة تشغيل الخدمة. إيقاف الاتصال يدويًا من QIROX يفصل الجلسة؛ إعادة النشر وحدها لا يفترض أن تمسحها.

صلاحية الربط وإدارة QR والإعدادات محصورة بالمدير والمدير العام. الموظفون يستخدمون CRM التشغيلي ولا يحتاجون إلى صلاحية ربط الرقم.

## 2. أي واجهة API أستخدم؟

### أ. تكامل المشروع — الخيار المعتاد لبرنامج خارجي

المسار:

```text
POST /api/v1/projects/{projectId}/whatsapp
```

يُصدر المفتاح لمشروع/طلب محدد من لوحة **تكاملات المشروع**. المفتاح مربوط بذلك المشروع والبيئة، ويُرسل الطلب من خادم النظام الخارجي إلى رقم QIROX المتصل.

### ب. تكامل متجر عميل

إذا كان المفتاح مطلوبًا لمتجر QIROX محددًا، استخدم واجهة المتاجر:

```text
POST /api/v1/stores/whatsapp/messages
```

هذه المفاتيح مربوطة بمتجر واحد، وتدعم صلاحيات وإيقافًا وحصة استخدام شهرية أو كل شهرين وسجل حالة الإرسال. تُدار من **واتساب المتاجر** في لوحة الإدارة.

لا تستخدم مفتاح المتجر بدل مفتاح تكامل المشروع؛ لكل منهما عنوان وصلاحيات ونطاق مختلف.

لإصدار مفتاح متجر، افتح **واتساب المتاجر** أو استخدم المسار الإداري `POST /api/admin/store-whatsapp/keys` بعد تسجيل الدخول كمدير/مدير عمليات. اختر المتجر والصلاحيات، ثم خزّن `rawKey` الذي يظهر مرة واحدة. المفتاح يبدأ بـ `qrx_wa_live_`، ويُحصر في متجر واحد. الافتراضي 30 طلبًا في الدقيقة و1000 رسالة للحصة الشهرية؛ يمكن ضبط الحصة لتكون شهرية أو كل شهرين.

مثال طلب إرسال من خادم النظام الخارجي:

```bash
curl --fail-with-body --request POST \
  "https://qiroxstudio.online/api/v1/stores/whatsapp/messages" \
  --header "Authorization: Bearer ${STORE_WA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: order-2026-000184" \
  --data '{
    "recipient": {
      "phone": "+966501234567",
      "name": "اسم العميل"
    },
    "message": "تم استلام طلبك بنجاح."
  }'
```

يمكن قراءة آخر حالات الإرسال الخاصة بالمفتاح نفسه من:

```text
GET /api/v1/stores/whatsapp/messages?limit=50
```

أرسل `Authorization: Bearer ...` في هذا الطلب أيضًا. تقبل `limit` من 1 إلى 100. عند تشغيل Baileys، استخدم نص `message`؛ لا ترسل كائن `template` وحده وتتوقع أن يتحول تلقائيًا إلى نص.

## 3. إنشاء مفتاح تكامل المشروع

1. افتح تفاصيل طلب/مشروع العميل ثم قسم **تكاملات المشروع**.
2. اختر **WhatsApp Business** أو تكامل WhatsApp.
3. اختر البيئة: `development` للاختبار، أو `staging` للتجربة قبل الإنتاج، أو `production` للاستخدام الحي.
4. حدّد اسمًا وحدّ الطلبات في الدقيقة، ثم أنشئ المفتاح.
5. انسخ المفتاح عند ظهوره واحفظه فورًا في Secrets/Secret Manager الخاص بخادم العميل.
6. أعطِ المبرمج رابط API ومعرّف المشروع، لكن لا ترسل المفتاح في مستودع Git أو محادثة عامة.

يمكن للإدارة إنشاء التكامل عبر جلسة QIROX المصرّح بها من:

```text
POST /api/admin/orders/{orderId}/integrations
```

مثال جسم الطلب الإداري:

```json
{
  "type": "whatsapp",
  "environment": "production",
  "label": "نظام الحجوزات",
  "rateLimitPerMinute": 30
}
```

هذا المسار إداري وليس للمبرمج الخارجي. المبرمج الخارجي يحتاج فقط إلى رابط الإرسال والمفتاح الذي تم إنشاؤه له. رابط `apiBaseUrl` الذي يظهر في بيانات التكامل هو المرجع؛ استخدمه كما هو بدل تركيب الرابط يدويًا.

### حماية المفتاح

- مفتاح المشروع يكون بصيغة `qrx_project_whatsapp_...`، ويُعرض سرّه مرة واحدة فقط.
- قاعدة البيانات تحفظ بصمة المفتاح، لا قيمته الخام.
- إذا انكشف المفتاح، عطّل التكامل ودوّر المفتاح من لوحة الإدارة، ثم حدّث Secret Manager في النظام الخارجي.
- لا تضع المفتاح في تطبيق المتصفح أو تطبيق الهاتف؛ أي مستخدم يستطيع استخراج أسرار الواجهة. اجعل تطبيق العميل يطلب الإرسال من خادمه، والخادم وحده يتصل بـQIROX.
- استخدم HTTPS فقط.

## 4. مواصفات طلب الإرسال

الرؤوس المطلوبة:

```text
Authorization: Bearer <QIROX_WA_API_KEY>
Content-Type: application/json
Idempotency-Key: <معرّف فريد من 8 إلى 160 حرفًا>
```

جسم رسالة نصية:

```json
{
  "recipient": {
    "phone": "+966501234567",
    "name": "اسم العميل"
  },
  "message": "تم تأكيد موعدك يوم الأحد الساعة 10 صباحًا."
}
```

اكتب الرقم بصيغة دولية E.164، مثل `+966501234567` للسعودية. لا تستخدم رقمًا محليًا غير واضح مثل `050...`.

توجد أيضًا حقول توافقية للمشاريع التي تبني الرسالة بهذه الصيغة:

```json
{
  "recipient": { "phone": "+966501234567", "name": "اسم العميل" },
  "platformName": "نظام الحجوزات",
  "clientName": "اسم العميل",
  "message": "تم تسجيل حجزك بنجاح."
}
```

إذا لم يُرسل `message`، يستطيع المسار تركيب نص مختصر من `platformName` و`clientName` و`verificationCode` أو `code`. لا تستخدم هذه الحقول لإرسال كلمات مرور أو مفاتيح أو معلومات استرداد. جسم الرسالة يُحفظ ضمن سجل التسليم لأغراض المحاولة والتدقيق؛ لا ترسل بيانات سرية أو حساسة.

### مثال `curl`

شغّله من خادم النظام الخارجي، بعد ضبط `QIROX_WA_API_KEY` و`QIROX_PROJECT_ID` في مدير الأسرار:

```bash
curl --fail-with-body --request POST \
  "https://qiroxstudio.online/api/v1/projects/${QIROX_PROJECT_ID}/whatsapp" \
  --header "Authorization: Bearer ${QIROX_WA_API_KEY}" \
  --header "Content-Type: application/json" \
  --header "Idempotency-Key: booking-2026-000184" \
  --data '{
    "recipient": {
      "phone": "+966501234567",
      "name": "اسم العميل"
    },
    "message": "تم تأكيد موعدك يوم الأحد الساعة 10 صباحًا."
  }'
```

استبدل `booking-2026-000184` بمعرّف ثابت وفريد للعملية في نظامك. إذا أعاد الخادم خطأ شبكة وأعدت الطلب للعملية نفسها، أعد استخدام المفتاح نفسه. لا تستخدمه لرسالة مختلفة.

### مثال Node.js

```js
import { randomUUID } from "node:crypto";

const baseUrl = process.env.QIROX_API_BASE_URL; // رابط apiBaseUrl المخصص للمشروع
const apiKey = process.env.QIROX_WA_API_KEY;    // Secret في الخادم فقط

if (!baseUrl || !apiKey) {
  throw new Error("QIROX API integration is not configured");
}

const response = await fetch(baseUrl, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${apiKey}`,
    "Content-Type": "application/json",
    "Idempotency-Key": randomUUID(),
  },
  body: JSON.stringify({
    recipient: {
      phone: "+966501234567",
      name: "اسم العميل",
    },
    message: "تم تأكيد موعدك يوم الأحد الساعة 10 صباحًا.",
  }),
});

const result = await response.json();
if (!response.ok) {
  throw new Error(`QIROX WhatsApp API returned HTTP ${response.status}`);
}

// 202 وقبول الطلب لا يعنيان بالضرورة أن هاتف المستلم استلم الرسالة بالفعل.
console.log({
  deliveryId: result.delivery?.id,
  status: result.delivery?.status,
});
```

### مثال Python

```python
import os
import uuid
import requests

base_url = os.environ["QIROX_API_BASE_URL"]  # رابط apiBaseUrl المخصص للمشروع
api_key = os.environ["QIROX_WA_API_KEY"]     # Secret في الخادم فقط

response = requests.post(
    base_url,
    headers={
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json",
        "Idempotency-Key": str(uuid.uuid4()),
    },
    json={
        "recipient": {
            "phone": "+966501234567",
            "name": "اسم العميل",
        },
        "message": "تم تأكيد موعدك يوم الأحد الساعة 10 صباحًا.",
    },
    timeout=20,
)
response.raise_for_status()
result = response.json()
print({
    "deliveryId": result.get("delivery", {}).get("id"),
    "status": result.get("delivery", {}).get("status"),
})
```

## 5. الاستجابة والأخطاء

الطلب المقبول يرجع عادةً `202` مع سجل التسليم:

```json
{
  "ok": true,
  "delivery": {
    "id": "معرّف-التسليم",
    "status": "pending"
  }
}
```

`202` أو `pending` يعني أن QIROX قبل الطلب للمعالجة، وليس تأكيد وصول الرسالة إلى المستلم. قد تتغير الحالة إلى `retrying` أو `sent` أو `failed`.

أهم الحالات:

- `400`: رقم أو جسم رسالة أو مفتاح Idempotency غير صالح.
- `401`: المفتاح مفقود أو غير صحيح.
- `403`: التكامل معطل/منتهي، أو نوع المفتاح لا يطابق المسار، أو أصل غير مسموح.
- `404`: معرّف مشروع غير صالح أو غير موجود.
- `429`: تجاوز الحد؛ انتظر قبل إعادة المحاولة.
- `500`: تعذر إنشاء طلب التسليم؛ راجع سجل الخدمة، ولا تسجل المفتاح أو بيانات المستلم السرية.

حد الرسالة النصية في واجهة المشروع 4000 حرف. الحد الافتراضي 30 طلبًا في الدقيقة لكل تكامل، ويمكن للإدارة ضبطه حتى 300. استخدم مفتاح Idempotency جديدًا لكل عملية إرسال مستقلة؛ التكرار بسبب إعادة المحاولة يجب أن يستخدم المفتاح نفسه.

## 6. إعدادات مزوّد واتساب والرقم المرسل

في إعداد QIROX الحالي، الاتصال الأساسي هو جلسة WhatsApp Web عبر Baileys والـQR، وبيئة Render محددة على `WHATSAPP_PROVIDER=baileys`. لذلك ترسل واجهة المشروع من رقم QIROX المشترك المتصل في CRM، لا من رقم هاتف يملكه النظام الخارجي.

يوجد مسار Meta اختياري عند ضبط `WHATSAPP_PROVIDER=meta` مع بيانات Meta في أسرار الخادم. الإعداد الحالي يستخدم متغيرات مزود عامة على مستوى الخدمة؛ لا يوفّر ربط رقم Meta مستقلًا لكل عميل. لا تغيّر المزود العام من أجل تكامل واحد قبل مراجعة أثره على بقية إشعارات QIROX.

**ملاحظة للمطوّر:** وصف بطاقة WhatsApp في واجهة تكاملات المشروع قد يقول «إرسال رسمي عبر Meta»، بينما مسار الإرسال الفعلي في الإعداد الحالي يستخدم Baileys. اعتمد على `WHATSAPP_PROVIDER` ومسار الخادم، وصحّح وصف الواجهة قبل تسليم المنتج حتى لا يُفهم أن الإرسال الحالي يتم عبر Meta Cloud API.

إذا كان المطلوب أن يربط كل عميل **رقمه الخاص** ويرسل منه، فهذا غير متاح عبر مفتاح المشروع الحالي. يلزم بناء تكامل مستقل متعدد العملاء مع WhatsApp Business Platform/Cloud API، وربط وموافقة كل حساب ورقم على حدة، وتخزين أسراره لكل مستأجر، ومعالجة Webhooks وحالة الرسائل. لا تشارك جلسة QR الخاصة بـQIROX ولا مفتاحًا عامًا بين العملاء.

## 7. الامتثال وسلامة الإرسال

- أرسل رسائل مرتبطة بخدمة طلبها المستلم أو بموافقة مسجلة منه.
- لا تستخدم API لإرسال رسائل عشوائية أو قوائم مشتراة أو رسائل متكررة غير مرغوبة.
- احتفظ بسجل موافقة المستلم ومصدرها وتاريخها في نظام العميل، وأوقف الإرسال فور طلب الإلغاء.
- طبّق قائمة منع للإرسال بعد الانسحاب، وحدودًا يومية وتجريبية، ومراقبة للأخطاء قبل توسيع الاستخدام.
- ابدأ بإرسال اختبار إلى رقم تملكه، ثم مجموعة صغيرة من مستلمين وافقوا صراحةً.
- لا ترسل كلمات المرور أو رموز الاسترداد أو بيانات الدفع. إذا كان الاستخدام لإشعارات تحقق حساسة، صمّم تخزينًا قصير العمر وإخفاءً للرموز في السجلات أولًا.
- استخدم قوالب Meta المعتمدة فقط عند تشغيل مزود Meta، والتزم بقيود Meta والقوانين المحلية. في إعداد Baileys الحالي استخدم نص `message` ولا تفترض أن قالب Meta سيُرسل كقالب رسمي.

## 8. التوثيق والاختبار

التوثيق العام الحالي:

```text
GET https://qiroxstudio.online/api/v1/projects/integrations/docs
```

اختبر بالترتيب:

1. تحقق من ظهور رقم QIROX كـ **متصل** في WhatsApp CRM.
2. أنشئ مفتاحًا لبيئة `development` أو `staging`.
3. أرسل رسالة واحدة إلى رقم تملكه أو لديك موافقة صاحبه.
4. تحقق من `deliveryId` والحالة في سجلات QIROX.
5. اختبر أن المفتاح المفقود أو المعطل مرفوض، وأن الحد يعيد `429`.
6. بعد نجاح الاختبار فقط أنشئ مفتاح `production`، وخزّنه في Secret Manager للنظام الخارجي.

لا يوجد في واجهة تكامل المشروع العامة حاليًا مسار مستقل للاستعلام عن حالة التسليم باستخدام `deliveryId`. إذا احتاج النظام الخارجي تحديثًا لاحقًا للحالة، أضف Webhook موقّعًا أو مسار استعلام محميًا قبل اعتباره مكتملًا.
